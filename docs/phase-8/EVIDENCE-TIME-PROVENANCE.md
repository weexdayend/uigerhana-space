# Phase 8.13 — Source-Run Report Time Provenance

**Status:** Instrumented; exact-head CI pending.  
**Scope:** Bind each evidence report to the GitHub Actions run that produced its artifact. This is a provenance check, not an evidence-age policy or release approval.

## Problem

The consolidated evidence manifest already bound each artifact to a unique source run ID, exact workflow path, dispatch event, conclusion, commit SHA, artifact name, and SHA-256 digest. It did not bind the report's own timestamp to the source run's lifetime. A report generated by an earlier run could therefore be replayed into an otherwise valid same-commit manifest if an artifact were copied or repackaged.

## Contract

The release gate records GitHub's `created_at` and `updated_at` values for each source workflow run. The evaluator then requires:

1. Both run timestamps are valid and the run's `updated_at` is not earlier than `created_at`.
2. The report timestamp falls within that exact run window:
   - External destination audit: `checkedAt`
   - Production parity audit: `checkedAt`
   - Physical-device evidence validation: `validatedAt`
3. The consolidated manifest is generated at or after the source run's `updated_at` time.

The manifest timestamp retains millisecond precision to avoid silently losing ordering information when GitHub returns sub-second timestamps.

## What this proves

It makes a report from one workflow execution ineligible for pairing with a different run ID, even when both executions target the same commit and use the same artifact naming convention. The existing commit, workflow-path, artifact-name, SHA-256, path-containment, and report-schema checks remain in place.

## What this does not prove

- It does not prove that owner-entered physical-device observations are truthful; the owner attestation and attachments still require human review.
- It does not prove served revision-marker provenance.
- It does not define a maximum age for a completed audit. No arbitrary freshness duration is introduced. The owner must set an acceptable freshness window before relying on the package for a release decision.
- It does not grant release or deployment authority. The report must always retain `releaseApproved: false` and `releaseDecision: "owner-review-required"`.

## Regression coverage

The evaluator tests reject report timestamps outside the source run interval, manifests generated before a source run completes, and physical-device reports without a validation timestamp. Workflow contract tests verify that all three source-run time windows are captured and the physical validator emits `validatedAt`.
